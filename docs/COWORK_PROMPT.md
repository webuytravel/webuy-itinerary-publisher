# 在 Cowork 里跑这套流程

给业务同事的交付件。**你不需要会写代码**——写代码的是 Claude,你负责的是判断和签字。

> 这是「今天就能用」的办法,不是最终形态。最终要做成 Skill / MCP 的方案见
> [docs/PRODUCTIZATION.md](PRODUCTIZATION.md)。

## 一、开始之前要有的三样

| | 要什么 | 怎么确认 |
|---|---|---|
| 1 | **仓库** | 在 Cowork 里打开 `webuy-itinerary-publisher`(公开仓库,直接 clone) |
| 2 | **Skybear 登录态** | 你自己在浏览器里登录 `travel.webuysg.com` 并保持登录。**Claude 不会、也不该替你输密码** |
| 3 | **行程册 PDF** | 放在你本机能读到的地方 |

不需要任何 API key、数据库密码、`.env`。原因见 [docs/SETUP.md](SETUP.md)。

> **2026-09-11 起不再需要 Chrome 扩展。** 新建产品走后端接口
> (`docs/UPLOAD_RUNBOOK.md` 5.5),传图用 `ttPackage/uploadImage`,不再依赖扩展的
> `file_upload`,也不再需要对着表单 DOM 一格一格填。原来那条路仍然留着(改已有
> 产品的图还在用),但**新册子默认走接口**:它快得多,而且不会因为 Skybear 前端
> 重新构建就失效——2026-09 那次重新部署验证过,后端一个字段都没动。

### 借一次登录态:唯一需要你动手的技术步骤

接口要带着你的登录身份去调,所以要把浏览器**已经在发的**请求头借出来一份。
全程不涉及密码,Claude 也没有任何账号。

1. 在已登录的 `travel.webuysg.com` 标签页按 F12 打开 Console;
2. 把 `lib/skybear_api.js` 的内容整个粘进去回车;
3. 再跑这两行:

```js
await SB.captureHeaders();   // 页面会自己跳一下 dashboard 再跳回来,这是正常的
copy(SB.headersJSON());      // 已复制到剪贴板
```

4. 粘进一个**仓库外面**的文件,例如 `~/sb_headers.json`,把路径告诉 Claude。

这份东西是一个**活的会话令牌**:不要提交进仓库、不要发群里,你退出登录它就失效。
过期了(Claude 会报 `4003 Illegal Token`)重做一遍这四步即可。

## 三、过程中你要做的判断

大约三次,每次 Claude 都会停下来等你:

**1. Highlights 怎么取舍。** 册子上有十几条,表单只有 6 格。Claude 会把原始条目和
它的取舍一起给你看。看的是:头部四条有没有把最能卖的东西放上去,餐食两条有没有
漏掉招牌菜。

**2. 配图审核页。** 一个网页,每张图标了来源和判定理由。**重点看外部图源那些**
——它们的典型错法是「主体对、地方不对」:搜西夏陵返回兵马俑,搜驼车返回单峰驼加
南亚服饰。你比 Claude 更清楚这条线路实际长什么样,看着不对就说。

页首如果有红色的「有景点却没有配图」,那是四级图源都没找到合规实拍,要你决定:
留空、你自己提供照片、还是改用当天城市的实拍。

**标准是:除了纯回程那一天,每天都该有图。** 抵达日虽然也在飞,但落地当天有
行程,它算正常的一天——线上在售的 10 天产品里,只有最后一天是没有配图的。

## 三点五、在 Skybear 页面上数图片,别用眼睛数

编辑页打开时**只有 Section 1 是展开的**,其余八天全折叠,里面的图一张都看不见;
而 Section 1 又常常正是抵达日。所以第一眼很容易看成「大部分天都没有照片」。

要数就让 Claude 把**逐日配图张数表**打给你(它读的是组件里的真实值,不是画面),
或者自己把每一天点开再看。2026-08-13 就发生过一次:页面上看着「8 天里只有 3 天
有照片」,实际是 9 天里 7 天有——但**确实少了 D1**,所以这个反馈是对的,只是
数字不对。

**3. 正式写之前的 dry run。** Claude 会先跑一遍不写库的预演,打出
「thumbnail=1 desktop=8 mobile=8 section=11 trip=23」这样一行。看的是 section
数量对不对得上天数——`section=8` 而行程是 12 天,就是有四天没图。

走接口这条路之后,**发布框不再需要靠截图确认**:`bin/api_upload.py` 里写死了
`travelStatus != 0` 就拒绝执行,payload 带 id(那是改已有产品)也拒绝。写完它会
自己回读一遍打给你看。

## 四、什么时候该停下来找工程

- **查到该 type_code 已经有 Published 的展示产品** —— 那是内容刷新不是新建,
  新建只会造出重复产品
- **没有团期** —— 数据模型上产品不能先于团期存在,要产品组先开团期
- **册子上有必需自费、强制小费、单房差这类条目** —— 当前流程没有字段承载它们,
  别因为表单里没地方放就当它不存在
- **Claude 说浏览器标签页卡死了** —— 只会发生在老的表单那条路上(见手册第 5 步),
  开新标签页重来即可;表单在点 Save 之前什么都不写库,重来是安全的。走接口没有
  这个问题

## 五、一个已知的粗糙处

每做一个新产品,Claude 都要往 `bin/make_payload.py` 和 `bin/compose.py` 里加几段
per-product 的配置(6 条 highlights、哪天用哪张图、8 张轮播)。这在 Cowork 里
是自动发生的,你不用管,但它意味着**每个产品都会产生一次代码改动**,需要有人
把这些改动提交回仓库。

这是当前形态的代价,也是 [docs/PRODUCTIZATION.md](PRODUCTIZATION.md) 要解决的
主要问题:把这些编辑决策从源码里搬到数据文件,让它变成配置而不是代码。
